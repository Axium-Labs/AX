# 审查与维护贡献

<a id="roles-and-authority"></a>
## 角色与权限

- **贡献者：**提出聚焦变更，按需取得设计同意，提供适当测试和文档，如实报告验证并回应审查。发起 PR 不获得合并权限。
- **审查者：**任何社区成员都可检查、测试 PR、识别风险并建议改进。发现须有证据，区分正确性／安全必改项与可选建议。社区批准是反馈，不是合并许可。
- **维护者：**确定范围与设计方向，解决冲突意见，评估验证，最终有权接受、拒绝、关闭或合并 PR。仓库写权限仍由维护者管理。

没有额外贡献者等级或强制审查委员会。

<a id="review-criteria"></a>
## 审查标准

以当前[架构](../architecture.zh-CN.md)、[开发](../development.zh-CN.md)、专题和已接受 [ADR](../adr/README.zh-CN.md) 为技术标准。针对变更行为检查以下问题，不适用区域需解释。

- **架构与 crate 边界：**变更是否属于承担对应职责的 crate？是否保留依赖方向、CLI 组合，以及内核与任务专属行为分离？重要偏离是否通过 ADR 讨论并记录？
- **Runtime 与 Agent Loop：**模型／工具／事件顺序、上下文预算、续接、终止、错误及恢复是否符合[运行时](../agent-runtime.zh-CN.md)和[循环](../agent-loop.zh-CN.md)契约？涉及时检查取消、截止、清理、子隔离和并发，排查死锁、无界重试和重复执行。
- **Memory 与 Storage：**[记忆](../memory.zh-CN.md)作用域／标识边界及[存储](../storage.zh-CN.md)语义是否成立？检查增量迁移、已有数据兼容、原始 JSONL 历史、恢复及部分写入。测试用隔离数据，证明状态不丢失、不跨项目／会话混合。
- **权限、安全与沙盒：**核对工具权限声明、显式拒绝／审批、独立[主机访问](../host-permissions.zh-CN.md)、隔离、子进程／MCP 边界及秘密。对照[安全](../security.zh-CN.md)与平台限制，动作审批不能静默绕过操作系统隔离。成功之外也审查对抗和拒绝路径。
- **性能与资源：**是否保留惰性初始化？热路径／启动路径改变时要求可复现前后测量，包含负载与环境。评估有界内存、并发、I/O、延迟、进程生命周期和清理，不接受无依据的速度结论。
- **测试与回归风险：**测试是否覆盖失败和新行为，以及相关错误与平台？最终公开文件集能否独立构建？是否区分私有结果、已跟踪工作区覆盖和仅编译检查？
- **公共 API、提供商、MCP 与依赖：**检查导出 Rust 类型、CLI／配置／事件及协议兼容、错误和迁移需求。相关时核对[提供商](../providers.zh-CN.md)与 [MCP](../mcp.zh-CN.md) 协商、流式、取消及认证。解释新依赖、许可／MSRV／平台影响和有意锁文件变更，避免不必要依赖及无关升级。
- **文档：**用户和开发者能否理解最终行为、限制及兼容性？是否同步更新专题、示例、链接和相关 ADR，同时不重复开发标准？

<a id="constructive-review"></a>
## 建设性审查

先看目的和主要风险，再看风格细节。引用受影响路径或契约，说明后果及验证修复方式。可选细节标为不阻塞，必改要求应可执行；缺少证据时询问。尊重地讨论分歧，未解决的设计和范围问题由维护者裁定。

更新后审查修改区域，核实旧问题已解决。批准旧版本不证明新行为正确。接手停滞工作前询问贡献者计划并保留署名，见[协调](issues.zh-CN.md#claim-and-coordinate-work)。

<a id="merge-gate"></a>
## 合并条件

合并前维护者确认：

1. 范围适当，所需 issue 设计同意已取得，重要决策已纳入 ADR 流程。
2. 正确性、安全、兼容及架构实质问题已解决，维护者已审最终版本；CI 不能替代审查。
3. 最终版本所需 PR 检查通过，适用平台及集成证据充分。环境限制有记录，由维护者决定合并前还需何种证据；限制不能成为隐藏失败检查的理由。
4. 测试和文档符合行为，依赖／API 变更有解释，已提交文件不依赖私有资源即可工作。
5. PR 可合并且聚焦，不含凭据、本地日志、私有测试产物或无关变更。

这些是审查策略。添加工作流不会配置 GitHub 分支保护或必需检查，相关设置由维护者独立管理。维护者保留最终合并决定，并解释拒绝或关闭原因。本指南不增加发布权限。
